## Indexes
@P I add few indexes beyond the ones constraints already create. A new index makes every write slower and takes space, so each one below earns its place by a named query. Ten are created on purpose.
@TBL 9
Index | Table | Columns | Query it serves
trip_requested_created_at_idx | trip | (created_at) WHERE status = 'requested' | A2 open requests near a driver and the request timeout job; a partial index holds only waiting trips
vehicle_driver_id_idx | vehicle | (driver_id) | A2 find the driver's vehicle; also supports vehicle_driver_id_fkey
trip_status_history_trip_seq_idx | trip_status_history | (trip_id, seq) | A3 status timeline ordered by seq; also supports history_trip_id_fkey
location_ping_trip_recorded_idx | location_ping | (trip_id, recorded_at DESC) | A3 latest driver position for the rider's map; also supports ping_trip_id_fkey
refund_payment_id_idx | refund | (payment_id) | the refund total check (B10); also supports refund_payment_id_fkey
trip_rider_history_idx | trip | (rider_id, created_at DESC, id DESC) | rider history list pages with keyset pagination; also supports trip_rider_id_fkey
trip_driver_history_idx | trip | (driver_id, created_at DESC, id DESC) | driver history list pages with keyset pagination; also supports trip_driver_id_fkey
payment_pending_created_at_idx | payment | (created_at) WHERE status = 'pending' | reconciliation job for pending payments older than a setting
provider_event_reference_idx | provider_event | (provider_reference) | the P3 lookup in payment_enforce_rules
payment_trip_id_idx | payment | (trip_id) | EP03 every payment of a trip (any status, so a failed attempt stays visible), EP15 and the support payment views
@END
@P The other 32 indexes exist because a constraint made them: PK and UNIQUE constraints create their own index.

## The statements that enforce the rules
@P B0, B1, B2: ACTIVE means requested, assigned, arrived, started. A trip with no driver has an empty driver_id, which never collides in the driver index, so it counts for the rider only. A partial unique index makes two active trips impossible, one per rider and one per driver.
@CODE
CREATE UNIQUE INDEX trip_one_active_per_rider ON trip (rider_id)
  WHERE status IN ('requested','assigned','arrived','started');
CREATE UNIQUE INDEX trip_one_active_per_driver ON trip (driver_id)
  WHERE status IN ('requested','assigned','arrived','started');
@END
@P A4, B6: one live (pending or succeeded) payment per trip and purpose. A failed one does not block a retry.
@CODE
CREATE UNIQUE INDEX payment_one_live_per_purpose ON payment (trip_id, purpose)
  WHERE status IN ('pending','succeeded');
@END

### An index added in Stage 4: the payments of a trip
@P In migration 016 an ordinary index was added on payment (trip_id), serving A4, B6, U1, U3 (EP03 payments of a trip, EP15 payment lookup per trip, support payment views). The only index that starts with trip_id on payment is payment_one_live_per_purpose, which is PARTIAL (pending and succeeded only), so a read of every payment of a trip (any status) could not use it and was a parallel sequential scan of the whole table (169,410 rows); the foreign key payment_trip_id_fkey also had no index on its referencing column.
@CODE
CREATE INDEX payment_trip_id_idx ON payment (trip_id);
@END
@P Before migration 016 the P1 read of all payments of a trip (every status), run 1, was:
@CODE
 Gather (actual time=9.595..17.314 rows=1 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   Buffers: shared hit=3427
   ->  Parallel Seq Scan on payment (actual time=8.226..9.490 rows=0 loops=3)
         Filter: (trip_id = '40000000-0000-0000-0000-000000198904'::uuid)
         Rows Removed by Filter: 56470
@END
@P After migration 016 the same read, run 1, is:
@CODE
 Index Scan using payment_trip_id_idx on payment (actual time=0.073..0.074 rows=1 loops=1)
   Index Cond: (trip_id = '40000000-0000-0000-0000-000000198904'::uuid)

@END
