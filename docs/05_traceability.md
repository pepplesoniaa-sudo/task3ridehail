## Coverage flags

- **PARTIAL B3:** the database cannot stop a decimal such as 10.5 (it rounds it to 11, CONFIRMED). Only API validation does, so B3 is fully covered only once the API stage writes that validation.
- **PARTIAL B8:** soft delete, anonymising and the blanking of text are designed. Retention periods are NOT verified, no deletion job for `location_ping` exists, and coordinates inside `fare_quote` are not erased. The conflict with B4 needs your decision (decision 1).
- **PARTIAL B6:** the database stops the second row. Returning the stored answer is application code (HQ6 table of invalid states).
- **GAP Q5:** no coverage on purpose. It is blocked on legal advice, and no retention period is chosen.
- **GAP Q6:** no coverage on purpose. It needs an owner decision before launch and is not solved here. Until then the design charges the rider the fee if they cancel after assignment, even when the driver never arrives.
- **PARTIAL B9:** the timeout move is allowed for actor `system` by the database, but the timer is a scheduled job (application code, 03 section 8). `request_timeout_seconds` = 600 is a placeholder that needs owner approval. If the job is down, a rider stays blocked by B1 until they cancel.
- **PARTIAL A4 and B6:** a stuck payment has a way out (reconciliation job, then move P3 by support after a `payment_not_found` event). The job is application code (03 section 8). `payment_reconcile_after_seconds` = 900 is a placeholder that needs owner approval. If the job is down, payments stay pending.
- **PARTIAL U4:** a conflicting provider message is stored and flagged `needs_support`. The refund itself is made by hand at the provider and is **not** a money record: it is a KNOWN GAP (below). Its trace is `provider_event` plus `audit_log`.
- **No requirement ID is without any coverage** except the open questions Q5 and Q6, which have no mechanism, and that is what their status says.


## Known gaps and limits (for the write-up)

These are limits of this design, stated on purpose. None is hidden elsewhere.

1. **KNOWN GAP, manual refund of a failed payment.** When a provider reports success for a payment we had marked failed, support refunds the surplus by hand at the provider. There is no money record for it: no row in `refund`, and B10 is not checked for it. The trace is `provider_event` plus `audit_log` only. It is a non goal in 01 for this assignment (03 section 4a).
2. **Q5, location retention:** no retention period is chosen, so no deletion job for `location_ping` exists. Blocked on legal advice.
3. **Q6, a driver who never arrives:** the rider is charged the fee if they cancel after assignment. Recommended fix (a stated number of late minutes, held in a setting) is not built.
4. **B8, personal data:** NDPA 2023 was not read. Coordinates inside `fare_quote` are not erased. The B4 exception for five text columns needs the owner's approval.
5. **B3, decimal money:** the database rounds 10.5 to 11 silently. Only API validation stops it, and the API is not built.
6. **Two scheduled jobs** (request timeout, payment reconciliation) are application code that does not exist. If they are down, riders stay blocked until they cancel, and payments stay pending (03 section 8).
7. **Actor identity is claimed by the application.** The database checks that the claimed actor may make a move. It cannot prove who the actor is. A compromised `ridehail_app` role could claim `support` or `provider`.
8. **The dev login is a superuser** and bypasses privilege checks. The Stage 3 proofs ran as `ridehail_app` by `SET ROLE` from that login. **A real login test was added in follow-up 2** (temporary role `ridehail_login_test`, dropped afterwards): as a real login it could not insert history, could not update a rating, could request a trip, and `RESET ROLE`, `SET ROLE ridehail` and `SET SESSION AUTHORIZATION ridehail` all failed or had no effect. That test used one connection over the container address; no deployment login role exists, and no password is kept in this project.
9. **A superuser can still bypass the history and audit protection.** Since migration 010 the application role cannot insert a history or audit row, and the writers run as `ridehail_writer`. A superuser can still switch triggers off, change owners or write rows. The actor name stays claimed by the application (item 7).
10. **Almost no concurrency tests exist.** Two two-session tests were added in Stage 4: a second insert of the same idempotency key waits for the first and times out with 55P03 (`evidence/api_idempotency_concurrency_test.txt`), and a second move of the same trip waits for the first (`evidence/part_b_trip_row_lock_b.txt`). Nothing was run with two sessions at once on the same payment, refund or provider event, or for two drivers accepting the same trip. The row lock in `refund_enforce_total` and the unique-index behaviour under a race are reasoned, not shown.
11. **The bulk set was loaded by four parallel sessions with disjoint riders and drivers** (trips split by `t mod 4`, so no two sessions ever touched the same rider or driver). That is not a concurrency test. A real application has no such property.
12. **The trigger-written history times in the bulk set equal the load time.** Every row of a bulk trip was written in one load transaction, so `created_at` ties inside every trip and carries no information. `started_at` and `completed_at` of bulk trips also equal the load time. Bulk `created_at` on trips was set back by the seed.
13. **62 bulk trips (299 history rows) have a history row numbered out of order.** The `seq` of rows that existed before migration 010 was assigned in heap order, and later rows had been stored on earlier pages. The 12 small-set trips are correct. Rows written after migration 010 are correct by construction. **Decision (owner): accepted.** The 62 trips are left as they are; the bulk set is only for query plans and the 12 small-set trips are correct. A repair would need the append-only trigger switched off, and nobody approved that.
14. **Fare, quote validity and service-area settings were without value until Stage 4, and their values are still placeholders.** Four settings existed (fee 50000, rating window 7 days, request timeout 600, reconcile after 900) and the query that reads the fare and area keys (A1.2) returned 0 rows (CONFIRMED). The sample seed applied in Stage 4 added 10 placeholder rows (item 27); EP01 now finds all 8 keys it needs (CONFIRMED, `evidence/seed_sample_settings_ep01_after.txt`).
15. **`refund_payment_id_idx` has not been shown used** (the refund table has 1 row), and the A2 open-requests query costs more as the waiting list grows (it looks up every waiting trip's quote before it applies the rectangle).
16. **`trip_status_history_trip_idx` was dropped (migration 012)** after showing that only diagnostic proof statements used it. Indexes were then 41; they are now 42 after migration 016 (item 25).
17. **Temporary tables could subvert the triggers until migrations 013 and 014** (a temp table named like a real table was searched first, so audit and history rows could be lost and a forbidden move accepted). All 18 functions now end their search path with `pg_temp` (013), and the TEMP privilege is revoked from PUBLIC on the database (014), so `ridehail_app` cannot create a temp table. Both protections were proved on the real database. Items 21 and 22 list what was not tried.
18. **The actor is claimed, and a real login role shows it:** a login member of `ridehail_app` can set `app.actor_role` to `support` and use `add_support_note`. Only an authenticated application that sets the claim from the signed-in user prevents that. The database cannot.
19. **Lesson from the 62 trips (item 13):** numbering existing rows by `ADD COLUMN ... IDENTITY` follows the heap order, not an explicit order. Add an order column before the data, or number from an explicit order, and verify with the chain query.

20. **`pg_hba` trusts loopback and the local socket inside the container.** Any process in the container, including `docker exec psql`, connects as any role with no password. Only other addresses use `scram-sha-256` (CONFIRMED in the login-role test, which had to connect over the container address). Not changed. A deployment needs its own `pg_hba`.
21. **Only three table names were attacked** in the search-path proofs (`audit_log`, `trip_status_history`, `status_transition_rule`). The other tables the functions read rely on the same two protections (migrations 013 and 014) but were not each attacked.
22. **Timings vary by about 3 times between runs on this machine** (A2.1 1.1 to 3.5 ms, the trip insert 7 to 31 ms). Every millisecond figure in these documents is an order of magnitude.
23. **The two plans for the grader** are in `evidence/plans_for_grader.txt` (A2.1, A1.1, and the trip insert as a labelled extra). No plan claims an index that the plan does not show.

24. **Migration 015 (Stage 4 follow-up): one SQLSTATE per rule.** Every `RAISE EXCEPTION` of the triggers and functions carries its own code in the custom class `RH` (45 codes, 49 statements), so the API maps errors by SQLSTATE and not by message text. Owners, SECURITY DEFINER flags, search paths and grants did not change (CONFIRMED by a before and after catalogue comparison). All 45 codes were raised in tests; six cannot be raised by the application role (privilege first, or a state it cannot create) and one is dead under today's rule table (`evidence/untested_rh_codes_proofs.txt`, `06b_error_catalogue.md` section 3).
25. **Migration 016 (Stage 4 close): index `payment_trip_id_idx` ON payment (trip_id).** Found in Part B: reading every payment of a trip (EP03, `payments[]`) was a full scan of 169,410 rows (14.5 to 17.7 ms) because the only index starting with `trip_id` is partial. The foreign key `payment_trip_id_fkey` had no index on its column either. Now 0.06 to 0.10 ms. Indexes are now **42** (32 constraint-backed + 10 chosen). Serves A4, B6, U1, U3.
26. **The event stream EP27 (`GET /v1/trips/{trip_id}/events`) is a design, not built.** It serves A3 and B8 (a rider sees only their own trip; the stream is closed at token expiry). It reads `trip_status_history` by `seq` and `location_ping`, both already indexed. Nothing was streamed over HTTP (`08_real_time.md`). Notifications from the database (LISTEN and NOTIFY) were tested by hand, not wired in.
27. **Settings values are placeholders.** The sample seed `db/seed/seed_sample_settings.sql` was applied in Stage 4 (10 rows: base fare, per kilometre, per minute, quote life, service-area box, two job intervals), assumes the city is Lagos, and needs the owner (`09_open_items.md`).
